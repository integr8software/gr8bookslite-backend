# Access Control Phase 2 Entitlement Service

## Overview

Phase 2 extracts the enabled-module entitlement responsibility from `AccessControlService` into `EntitlementService`.

This is intentionally behavior-preserving. The runtime entitlement source is still `company_modules` through the Prisma relation `company.enabledModules`. No subscription-plan computation, override model, schema migration, API contract change, or frontend change is introduced in this phase.

## What Moved

The following enabled-module helpers moved into `EntitlementService`:

- Resolve enabled module codes.
- Resolve enabled module IDs.
- Filter enabled module records by the existing permission set.
- Check whether a module is available to an admin or to a user with at least one permission action.

`EntitlementService` files:

- `src/common/access/entitlements/entitlement.service.ts`
- `src/common/access/entitlements/entitlement.types.ts`
- `src/common/access/entitlements/entitlement.module.ts`

## What Stayed In AccessControlService

`AccessControlService` still owns orchestration and all non-entitlement behavior:

- Active user loading.
- Membership loading.
- Company/subscription availability checks.
- Permission aggregation.
- Permission override application.
- Sidebar filtering and tree building.
- `AuthUser` response assembly.
- Public methods:
  - `resolveAuthUser`
  - `hasPermission`
  - `assertCompanyContext`

## Behavior Preservation

The service still reads entitlements from the same loaded membership graph:

```text
membership.company.enabledModules
```

This maps to the existing `company_modules` compatibility table. The extracted service does not query subscription plans directly and does not infer modules from module systems.

Existing response fields remain unchanged:

- `enabledModules`
- `permissions`
- `userModules.items`
- `userModules.byBranch`

## Why Company Modules Remain The Compatibility Source

`company_modules` is still the production runtime source used by `AccessControlService`. Keeping it as the compatibility source avoids changing:

- login behavior
- `/auth/me`
- company switching
- branch switching
- sidebar rendering
- onboarding behavior stabilized in Phase 0
- legacy company behavior

Changing `company_modules` semantics should happen later inside `EntitlementService`, after the extraction boundary is proven.

## Future Entitlement Direction

Later phases can change `EntitlementService` internals to compute effective modules from:

```text
active subscription plan module systems
+ explicitly enabled company exceptions
- explicitly disabled company exceptions
```

That change should keep the `AccessControlService` call sites stable.

## Risks

- `company_modules` can still contain legacy over-granted rows from previous provision behavior.
- `EntitlementService` currently receives already-loaded module records; it does not own the Prisma include graph yet.
- Module filtering still depends on permission strings generated by `AccessControlService`.
- Sidebar building is still in `AccessControlService`, so entitlement and sidebar behavior are not fully separated yet.

## Phase 3 Recommendation

Extract `PermissionService` next, still behavior-preserving.

Recommended boundary:

- Input: membership permission records and enabled module codes.
- Output: same `permissionCode:action` string array.
- Preserve company role permissions.
- Preserve branch role permissions.
- Preserve user permission overrides.
- Preserve legacy module lookup compatibility.

Do not extract `SidebarBuilder` until entitlement and permission inputs are stable.
